# Future Node 1 调研报告（人话版）：DSH 多代理原语、SuperAgent 与编排插件怎么配合

> **原调研：** `2026-11-21` ｜ **更新：** `2026-11-22` ｜ **宿主：** DSH `0.2.2-rc.5` ｜ **官方原型：** `v0.1.0` ｜ **插件：** `@sshirkit/dsh-orchestrator` `0.9.2` ｜ **状态：** 静态源码调研；路线已由维护决策 ADR-0004 拍板，尚未交付

## 一、一句话结论

**DSH 核心提供多代理原语，官方 SuperAgent 原型接外部工单，`dsh-orchestrator` 负责本地交互式研发中单个任务的强治理与可靠性编排。** 正式适配团队任务板、协调跨重启唤醒，但不把上下文继承或宿主脚本编排接入插件主工作流。

---

## 二、先正名：DSH 核心和 SuperAgent 原型是两层

本机 DSH `0.2.2-rc.5` 的 `app.asar` 核心源码没有内置名为 `superagent` 的模块。「DSH 原生 SuperAgent」容易把核心内置能力和官方独立原型混为一谈，下面分开说。

### 层 A：DSH 核心内置多代理原语

- **子代理与会话控制。** `dsh-subagent` 提供会话原语；`dsh-tool-subagent` 暴露 `subagent`（新开会话）、`subagent_fork`（继承父会话上下文）和 `list_subagent_models`；`dsh-tool-subagent-control` 提供 `send_message`、`list_agents`、`wait_agent`、`interrupt_agent`。子代理可用不同于主代理的模型，但候选模型受会话级白名单快照约束，全局设置变化不会自动改写旧会话的快照。
- **团队任务板。** `dsh-agent-team` 的开关按根会话设置，子代理继承。开启后，子代理目录下显示持久化共享任务板；`team_task_create` / `team_task_list` / `team_task_get` / `team_task_update` 支持依赖关系和 CAS 版本校验。任务变为 `ready` 只是可认领，不会自动唤醒或派发子代理；写范围重叠也只提醒，不拦派发。
- **代码式批量编排。** `dsh-workflow-ptc` 在沙箱里跑 Node.js 工作流，可用 `parallel()`、`pipeline()` 做高吞吐编排。它与 Python PTC 互斥；当前 `agent()` 不接受 `effort`，传入会报错。
- **工作树入口。** `dsh-experimental-tool-worktree` 只创建、切换 Git worktree，不负责评估、合并或清理，也不提供写锁。

### 层 B：官方 SuperAgent 研究原型

[deepseek-ai/dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype) `v0.1.0` 是独立 Bundle，不是 DSH 核心自带的模块。它更像一个 **7×24 后台工单值守 Daemon**：

- **接单和准入。** 接 GitHub / Feishu 事件，由 `Gate` 按版本化 `Policy` 判断事件能否进入和获得哪些授权。
- **任务推进和隔离。** SQLite 持久化状态机和 `Effects` 队列支持跨重启恢复；每张 Ticket 使用独立物理目录（`/work/<ticket>`），不等同于同一仓库里的路径级互斥。
- **监督和前后台分离。** 监督面板有 6 个 Tab；前台最多等待 5 秒，超时后不继续阻塞前台，后台任务仍可推进。

## 三、能力对比：插件 `0.9.2` 的六项优势

| 能力 | DSH 核心（层 A） | SuperAgent 原型（层 B） | `dsh-orchestrator` `0.9.2` |
| --- | --- | --- | --- |
| 主从权限 | 提供工具原语，默认不划分架构师和执行者的工具权限 | `superagent-router` 对其代理统一禁用 `web`、`todo`、`ask_user_question`、`subagent`，对交互式规划来说过粗 | **主从双闸门**：模型工具面隐藏 + 执行守卫，默认 12 项白名单；[`run_code` 词法守卫](../../lib/run-code-guard.js)再检查传输层是否试图绕开工具限制 |
| 同仓写冲突 | Team 只提示，worktree 不管锁 | 按 Ticket 物理目录隔离 | **同仓逻辑写锁**：派发前声明 `writeScope` 并申请进程内 [`write-lease`](../../lib/write-lease.js) 互斥租约；`delegate` 按子代理、`orchestrate` 按整批持锁，冲突拒绝派发 |
| 主从异构模型 | 支持异构模型，会话级候选白名单是快照 | 按原型的路由与 Policy 执行，不以交互选模为设计重点 | **全局解耦路由**：主、从默认路由独立配置，新派发实时读默认值，也可单次覆盖；Web 面板动态订阅 `ctx.modelDirectories` 的会话目录 |
| 巡检与纠偏 | 提供子代理状态和人工控制 | 用工单状态和 6 Tab 面板做值守监督 | **旁路只读巡检**：[`supervise.js`](../../lib/supervise.js) 定时读交互式子代理会话日志，发现重复调用、进展停滞等迹象时可通知并唤醒主代理纠偏 |
| 批量多阶段 | 用 JS 的 `parallel()` / `pipeline()` 自由编排 | 重点是工单状态转移和 `Effects` | **声明式流水线**：[`orchestrate`](../../lib/orchestrate.js) 对 `items × stages` 做严格 Schema 校验；同条目按阶段推进，不同条目之间没有全局阶段屏障，单条失败可隔离 |
| 中断恢复 | 有子代理控制和会话恢复原语 | 用持久状态机和 `Effects` 恢复后台工单 | **交互式冷恢复**：[`retry.js`](../../lib/retry.js) 对异常结束且没有收尾消息的已跟踪子代理做有界重试，冷唤醒原会话而不是另派一个子代理 |

**共存不等于重做。** 团队任务板直接对接宿主能力，不另造一份。上下文继承和宿主代码编排不进入插件主流程；原型的 SQLite 状态机与 `Effects` 队列、外部事件值守、版本化授权网关及 5 秒前台超时也不由插件重做。团队任务板的持久化不等于后台工单恢复；插件只协调宿主唤醒，并补齐自身所需的会话级状态。

## 四、同时使用，哪里容易打架？

1. **白名单先挡住了 Team。** 插件工具与核心工具不重名，但 `0.9.2` 的默认严格模式不放行 `team_task_*`、`list_agents`、`wait_agent` 等工具。正式兼容时按任务板需要适配权限，不等于允许根代理直接用 `subagent` / `subagent_fork` 派人。
2. **先说清谁派、谁管。** 当前巡检与冷恢复跟踪 `delegate` 派出的交互式子代理；`delegate` 和 `orchestrate` 共享租约表。直接用核心工具派出的子代理不会自动进入这些管控；如果工单层和插件同时重试同一任务，还可能重复执行。
3. **现有写锁只拦申报冲突，没闭环。** `writeScope` 目前必填，只读任务也得填；租约不是操作系统写权限，不审计实际写入。子代理结束时先释放锁，再评估重试，冷恢复前还没重新抢锁。
4. **UI 插槽能共存，私有接口要留退路。** 核心任务板在子代理目录下，插件设置在输入框侧；可以用 `subagent.footer` 展示插件状态。但裁剪工具列表用到宿主私有 `view()`，升版要探测能力并保留降级路径。

## 五、已定兼容边界与演进路线

以下是 ADR-0004 确认的路线，不是 `0.9.2` 已交付的能力。

### 兼容边界：哪些接，哪些只共存

| 能力 | 最终决定 |
| --- | --- |
| `dsh-agent-team` | **正式兼容。** 主、从代理通过原生共享任务板同步分工和状态；任务板不代替插件派发或写租约。 |
| `subagent_fork` | **默认禁用，仅底线兼容。** 不接入 `delegate` 或主工作流；宿主暴露时由白名单默认屏蔽，共存不报错即可。全量继承的父上下文带来高额且无法命中 Prompt Cache 的输入 Token；截取局部上下文与直接写精准 Prompt 无本质区别。 |
| `dsh-workflow-ptc` | **默认禁用，仅底线兼容。** 白名单默认屏蔽，不整合宿主沙箱化 JS 编排，继续以插件自有声明式 `orchestrate` 为主。 |
| GitHub / Feishu 事件与版本化 `Policy` 授权 | **主代理侧保留底线兼容。** 不自研外部值守和授权网关，共存时不误拦或破坏宿主相关能力。 |
| 跨重启恢复与唤醒 | **双向兼容、防冲突。** 对接宿主重启后自动唤醒中断子代理的能力，和插件自己的唤醒、重试协调去重，不复制原型的 SQLite 工单状态机和持久副作用队列。 |
| 5 秒前台超时 | **不做。** 规划主代理的白名单已经禁止耗时终端命令，无需复制原型的前台防阻塞机制。 |

### 自身优先级：先补治理闭环，再增强隔离和韧性

1. **着重处理 / P0–P1：写作用域闭环与显式只读。** 按 [Issue #1](https://github.com/SShiRkiT/dsh-orchestrator/issues/1) 补齐 AC5–AC8：执行后告警越界写，校验写后指纹，检查声明目标是否消失，并验证只读任务没有写权限。重试前重新抢占适用的写租约，没拿到不续跑。支持 `readOnly: true` 的零写权语义：不占写租约、不填虚拟 `writeScope`，只读子代理发生写操作即告警。零写权不能只靠提示词，宿主不能保证时不宣称已隔离。
2. **着重处理 / P1：运行期语义巡检。** 升级 [`supervise.js`](../../lib/supervise.js)，旁路读运行日志并分析行为与进度趋势，区分正常的长耗时推进和重复报错、原地打转、偏离目标目录，给主代理高信噪比诊断摘要。不要求最终交付报告填 `progress` / `blocked` 固定字段：交付时主代理已被唤醒，可以直接理解自然语言汇报。
3. **采纳 / P1–P2：Worktree 物理隔离与主代理评估合并。** 宿主实验工具只创建和切换目录。插件负责派发隔离副本，子代理独立修改，结束后提交 diff / 变更摘要供主代理评估。主代理决定合并或丢弃清理，可以派审查或合并子代理，但不自动盲合。同一工作目录仍需防止写冲突。
4. **采纳 / P2：会话级轻量跨重启持久化。** 保存写租约、未完成任务树和巡检基线。服务重启后核对并重建状态，与宿主原生唤醒协调，避免丢锁或重复拉起。
5. **明确不做：错误分级和智能重试。** 维持 [`retry.js`](../../lib/retry.js) 现有错误处理和重试策略，不给 `AUTH` 等错误加特殊熔断。重试前抢锁和跨重启去重是治理补强，不是调整什么错误该重试。

---

## 六、总结

长期定位是「`dsh-superagent` 做上游外部事件值守，插件做下游单任务内部强治理编排」。这是生态分工，不是当前的嵌套开发计划。眼下正式兼容团队任务板、协调恢复去重，优先补齐写治理和运行期语义巡检，再补 Worktree 评估合并和会话级持久化。
